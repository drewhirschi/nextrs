# Jobs live in a `jobs/` folder beside `app/`, any file, many per file

- **Reported-in:** design discussion with Drew (no app report)
- **Date:** 2026-11-24
- **Status:** open   <!-- set to `fixed in <commit>` when the PR lands -->
- **Related:** [vercel-queues-jobs-backend.md](vercel-queues-jobs-backend.md),
  [background-jobs.md](../background-jobs.md)

## Problem

A job had to be `app/jobs/<name>/job.rs`: one job per file, one directory
per job, named after the directory, inside the folder that otherwise means
"things with URLs". Drew's objections, in his words: "I don't really like the
idea of forcing them to be under jobs", "you don't want too much of your
logic directly in the app anyway. That's more just a controller", "You can
also define multiple jobs in a single file", and he wanted the import tree to
organize them.

## Proposed Direction

What most frameworks do (Rails `app/jobs/`, Laravel `app/Jobs/`, Trigger.dev
`trigger/`): a top-level folder for jobs, a sibling of the routes.

```text
app/                    routes and pages
jobs/
  todos.rs              audit_todo, reindex_todos
  billing/
    invoices.rs         send_invoice
src/                    domain logic the jobs call
```

- Every `.rs` file under `jobs/` is a module under `crate::jobs`; folders are
  namespaces. `jobs/billing/invoices.rs` is `crate::jobs::billing::invoices`.
- Every `#[nextrs::job]` function in those files is a job. Any number per
  file. A file with none is still a module (shared payload types).
- The job's name is the function name, or `name = "…"`. Never the file path:
  the name is what queued work refers to, so moving a file must not rename it.
- `app/jobs/<name>/job.rs` keeps working unchanged.

Not built: jobs tagged anywhere at all (for example in `src/`). That needs a
link-time registry (`inventory` or similar), untested on Vercel. A
configurable list of job folders would be the smaller step toward it.

## Implementation Notes

- **Macro** (`nextrs-macros`): generated items are suffixed with the function
  name (`__nextrs_job_run_<fn>`, `__nextrs_job_entry_<fn>()`), which is what
  allows several jobs per file. The entry function returns the whole
  `JobEntry`, so codegen only needs to know where a job is, not its settings.
  For `app/jobs/<name>/job.rs` the old fixed names are still emitted, so a
  registry generated by nextrs 0.7.0 keeps compiling against a newer macro.
- **Tagging outside the scanned folders is a compile error.** The macro
  checks its own file path. Without that, a job tagged in `src/` could be
  enqueued and would never run.
- **Enqueue also checks at run time** that the job's name is in a router this
  process built (`jobs::note_registered`), and returns a `Config` error
  naming the fix. This catches what the path check and the textual scan can
  miss (for example `use nextrs::job; #[job]`).
- **Build script**: `emit_registry` looks for `jobs/` beside the app
  directory, with no change to an app's `build.rs`. It scans textually, like
  the existing job and seed scans, skipping comment lines. Duplicate names,
  `mod.rs`, a file and a folder with one module name, and file names that are
  not identifiers are `compile_error!`s that name the files.
- **First `jobs/` folder in an existing app**: Cargo only reruns the build
  script when a watched path changes, and a folder that did not exist was not
  watched (watching a missing path would rerun the script on every build).
  Saving `build.rs` once, or restarting `nextrs dev`, picks it up. The
  scaffold creates `jobs/` so new apps never hit this.
- **Server bundles**: every bundle includes the whole `jobs/` folder. A
  directory under `app/` could assign a job to one bundle; a `jobs/` file
  cannot. The queue consumer runs every job anyway.
- react-todos' job moved to `jobs/todos.rs`, so its name changed from
  `audit-todo` to `audit_todo`.

## Validation

- `cargo test -p nextrs-macros`: place detection from the file path, naming,
  `name = "…"` and its validation, no collisions between two jobs in a file.
- `cargo test -p nextrs --features build,jobs`: scanning a folder with nested
  files, several jobs per file, a comment that mentions the attribute; the
  generated module tree and registrations; duplicate-name and layout errors;
  the enqueue guard.
- react-todos run locally: a `flaky:` todo fails, retries after 2 s, succeeds,
  logged under `react_todos::jobs::todos`.

  the PR description for what the logs showed.
